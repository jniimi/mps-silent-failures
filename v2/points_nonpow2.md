# 2 の冪でない shape の追試: 指定点と予測(実行前に記入)

`points_nonpow2.json` の 24 点(+ 較正 6 実行)を Studio(M2 Ultra 192 GB、torch 2.14.0、MPS)で実行する。予測は実行前に論文の 3 規則から要素単位で導いたもの。「観測」の列は実行後に埋める。

## 目的

既存の走査の shape はどれも行列 1 つが 2^16 要素なので、境界をまたぐ tensor の要素 2^31 / 2^32 は必ずバッチの境目に来る。そのため「制約は平坦な要素 index にかかる」と「バッチ数にかかる」を区別できない。ここではバッチあたり 62,500 = 250 × 250 要素の shape を使い、要素 2^31 / 2^32 がバッチの途中・行の途中に来るようにする。

- `in-250x250x64`: M = 250, K = 250, N = 64、cross = in。a が 62,500 / バッチ、b と出力が 16,000 / バッチ
- `out-250x64x250`: M = 250, K = 64, N = 250、cross = out。出力が 62,500 / バッチ、a と b が 16,000 / バッチ

規則(PyTorch 2.14.0、MPS の bmm、この順に適用):

1. 出力が 2^32 要素を超え、オペランドのどちらかが転置 view → 全バッチで黙って誤答(そのオペランドの stride を無視した計算と一致)。出力が 2^32 要素を超えても、転置 view がなければ正しい
2. view であるオペランド(転置 view、または storage_offset を持つ slice)が 2^31 要素以上 → 例外(`MPSGraph does not support tensor dims larger than INT_MAX`)
3. 連続なオペランドが 2^32 要素を超える → 要素 2^32 より後ろだけ黙って誤答(そのオペランドへの平坦 index が 2^32 で巻き戻る計算と一致)

## レイアウトごとの格納(worker.py の作り方どおり)

| レイアウト | a の格納 → bmm に渡す view | b の格納 → view | 論理要素 (i, r, c) の格納上の平坦 index |
|---|---|---|---|
| contig | (B, M, K) そのまま、offset 0 | (B, K, N) そのまま | i·rc + r·C + c |
| bT | a は contig と同じ | (B, N, K) の連続を `.transpose(1,2)`、stride (KN, 1, K) | b: i·KN + c·K + r |
| aT | (B, K, M) の連続を `.transpose(1,2)`、stride (MK, 1, M) | b は contig と同じ | a: i·MK + c·M + r |
| slice | (B+1, M, K) の [1:]。先頭に論理 index −1 の乱数バッチ。storage_offset = MK | (B+1, K, N) の [1:]、offset = KN | (i+1)·rc + r·C + c |

slice の view は `is_contiguous()` が真だが storage_offset を持つので、規則 2 の「view」に入る(既存の in-256x256x64 slice は B = 32768 で例外)。slice の格納は 1 バッチ多いので、格納上の要素 2^31 / 2^32 は view では 1 バッチ前に来る(in 側: 格納の要素 2^31 = 格納バッチ 34,359 の位置 46,148 = view バッチ 34,358)。ただし slice の view は規則 2 で 2^31 要素から例外になるので、規則 3 の領域(2^32)には届かない。out 側の slice はまたぐ量(出力)が slice ではないので、1 バッチのずれは境界の位置に影響しない。

## 算術(`uv run python` で検算済み)

- 2^31 = 2,147,483,648。2^31 / 62,500 = 34,359.738…
  - B = 34,359: 62,500 × 34,359 = 2,147,437,500(2^31 より 46,148 少ない)
  - B = 34,360: 62,500 × 34,360 = 2,147,500,000(2^31 以上、16,352 多い)→ a が 2^31 要素以上になる最初の B
- 2^32 = 4,294,967,296。2^32 / 62,500 = 68,719.476…
  - B = 68,719: 4,294,937,500(2^32 より 29,796 少ない)。最後の要素の index 4,294,937,499 < 2^32
  - B = 68,720: 4,295,000,000(2^32 より 32,704 多い)。要素 2^32(0 始まりの index 4,294,967,296)は バッチ ⌊2^32 / 62,500⌋ = 68,719 の位置 2^32 − 68,719 × 62,500 = 29,796 = 行 119、列 46(29,796 = 119 × 250 + 46)
  - B = 68,721: 4,295,062,500(2^32 より 95,204 = 32,704 + 62,500 多い)→ バッチ 68,720 は全体が 2^32 より後ろ。その先頭は 68,720 × 62,500 − 2^32 = 32,704 = 行 130、列 204 に巻き戻る
- slice(in 側)B = 34,359: view の要素数は 2,147,437,500 < 2^31。格納は 34,360 バッチ = 2,147,500,000 要素で、最後の格納 index 2,147,499,999 > INT_MAX = 2,147,483,647
- out 側の a, b: 16,000 × 68,720 = 1,099,520,000 < 2^31(規則 2 に当たらない)。in 側の b も同じ
- 規則 3 の巻き戻り: バッチ 68,719 の位置 p ≥ 29,796 は平坦 index p − 29,796(バッチ 0)から読む。バッチ 68,720 の位置 p は 32,704 + p から読む。p < 29,796 ならバッチ 0 の位置 32,704 + p、p ≥ 29,796 ならバッチ 1 の位置 p − 29,796
- 出力の行: in 側の出力 (m, n) は a の行 m(位置 250m 〜 250m + 249)全体に依存する。行 m が巻き戻った要素を含むのは 250m + 249 ≥ 29,796、つまり m ≥ 119 のとき。行 119 は列 46〜249 の 204 要素が巻き戻り、行 120〜249 は全体が巻き戻る
  - 乱数入力: バッチ 68,719 の出力の行 119〜249(131 行 × 64 列 = 8,384 要素)が誤答、行 0〜118 は正しい。平坦位置 r·64 + c は 7,616 (119,0) 〜 15,999 (249,63)
  - index 符号化 idx_a_*(b は選択行列 b[k, n] = [k = n]、出力 (m, n) = a[m, n]、n < 64): 出力 (m, n) が誤答になるのは a[m, n] の位置 250m + n ≥ 29,796 のときだけ。バッチ 68,719 では行 119 の列 46〜63(18 要素)と行 120〜249(130 × 64 = 8,320)の計 8,338 要素、平坦位置 7,662 (119,46) 〜 15,999
- 読み違えた値(index 符号化、B = 68,721)
  - idx_a_rc(a の値 = バッチ内の位置 + 1): バッチ 68,719 の誤答 8,338 要素は位置 p → p − 29,796 で delta = −29,796。バッチ 68,720 の 16,000 要素は、p < 29,796 の 7,662 要素(行 0〜118 の全列 7,616 + 行 119 の列 0〜45 の 46)が delta = +32,704(= 62,500 − 29,796)、p ≥ 29,796 の 8,338 要素が delta = −29,796
  - idx_a_batch(a の値 = バッチ index + 1): バッチ 68,719 の誤答はバッチ 0 を読むので delta = −68,719(8,338 要素)。バッチ 68,720 は p < 29,796 でバッチ 0(delta = −68,720、7,662 要素)、p ≥ 29,796 でバッチ 1(delta = −68,719、8,338 要素)
  - 比較は 536 バッチずつのブロックで行い、誤答はすべて最後のブロック [68,608, 68,721) に入る(24,338 要素 < 間引きの上限 65,536)ので、delta の要素数は間引きなしの厳密な値になる
- out 側の stride 無視(規則 1): bT なら b'[k, n] = 格納 (250, 64) の平坦位置 250k + n の値 = 論理 b[(250k + n) mod 64, ⌊(250k + n) / 64⌋]。b' = b になるのは 250k + n = 64n + k、つまり 83k = 21n の (k, n) = (0,0), (21,83), (42,166), (63,249) の 4 要素だけ。乱数入力では出力の各列が b の列全体を使うので全 62,500 要素が誤答(偶然に許容誤差内に入る要素がごくわずかある。既存の out-256x64x256 bT では frac_elem_bad = 0.99996)。idx_b_rc(a は選択行列 a[m, k] = [k = m mod 64]、出力 (m, n) = b'[m mod 64, n])では、m mod 64 が 0, 21, 42, 63 の行の該当列の 15 要素((0,0), (64,0), (128,0), (192,0), (21,83), (85,83), (149,83), (213,83), (42,166), (106,166), (170,166), (234,166), (63,249), (127,249), (191,249))だけが正しく、62,485 / 62,500 要素が誤答(既存の 256 版では 16 要素が正しく 0.999756、同じ導出で一致)。delta の値は 1 バッチあたり 8,818 種類に分かれ、単一のずれにならない(worker.hyp_operand で CPU 計算)

## 区別できること

- 平坦 index か、バッチ数か(規則 3): #4, #7 がこの追試の中心。規則 3 が要素単位の平坦 index の巻き戻りなら、バッチ 68,719 の中で出力の行 119 を境に正誤が分かれる。代わりに「バッチの先頭位置 i·62,500 だけが 32 bit で計算され、バッチ内の位置は別に足される」のであれば、バッチ 68,719 の先頭(4,294,937,500)は 2^32 未満なので #4, #7 は全体が正しく、#5 のバッチ 68,720 だけが(平坦 index の巻き戻りと同じ値で)誤答になる。バッチ単位の読み替え(バッチ i を別のバッチとして丸ごと読む)であれば、誤答はバッチの全行に出る
- 要素数か、バッチ数か(規則 1〜3 のしきい値): #3, #6(規則 3 の対象)と #18, #20(規則 1 の対象)はバッチ数 68,719 > 2^16 だが、またぐ tensor は 2^32 要素未満。しきい値がバッチ数 2^16 にあるなら、これらは誤答になる。#1, #8, #11 はバッチ数 34,359 > 2^15 だが 2^31 要素未満。規則 2 のしきい値がバッチ数 2^15 にあるなら、#8, #11 は例外になる
- 規則 2 は view の要素数か、格納の範囲か: #11(slice、B = 34,359)は view の要素数が 2^31 未満で、格納の最後の index が INT_MAX を超える。既存の 2 の冪の走査(in-256x256x64 slice B = 32767: view 2^31 − 2^16 要素、格納の最後の index = 2^31 − 1 = INT_MAX で ok)は「storage_offset + 要素数 ≥ 2^31 で例外」を否定するが、「格納の最後の index > INT_MAX で例外」とは区別できていなかった。#11 が ok なら規則 2 どおり(view の要素数)、error なら条件は格納の範囲
- 規則 1 の出力のしきい値: #18, #20(出力 4,294,937,500 < 2^32)は ok、#19, #21(> 2^32)は全バッチ誤答、と予測する。要素 2^32 は出力のバッチ 68,719 の途中(行 119、列 46)にあるが、規則 1 の誤答は位置によらず全バッチに出る

## 実行(Studio)

コードの変更を commit して Studio で pull してから(manifest に git の revision と dirty が残る):

```
cd ~/Documents/GitHub/mps-boundary/v2
uv run python scan.py --host-tag studio --points points_nonpow2.json --wandb --wandb-every 25
```

`--wandb` は退避で、なくてもよい。`--dtypes` は points モードでは使われない(dtype は各点に書いてある)。較正は点に出てくる (shape, dtype) の 2 組 × seed 3 = 6 実行(B = cal_B = ⌊2^28 / 62,500⌋ = 4,294)で、その許容誤差で 24 点を 1 回ずつ実行する。終了時に `results/summary/studio/<run_id>.md` が作られ、新しい節「誤答要素のバッチ内の位置」に bad_batch_detail と index 符号化の delta が載る。

- メモリ: 1 実行の host 見積もりの最大 28.4 GiB(device 上の a + b + 出力 ≈ 26.0 GB × 1.05 + 3 GiB)。Studio の上限は 192 GB × 0.6 ≈ 115 GiB

規則 3 の「要素単位の平坦 index の巻き戻り」という予測は外れた。観測は「区別できること」の 1 つ目に書いた対立仮説のとおりで、誤答になるのは先頭が要素 2^32 以降にあるバッチだけ。2^32 をまたぐバッチ 68,719(先頭 4,294,937,500 < 2^32)は正しい。先頭が 2^32 以降のバッチ 68,720 は、先頭の位置を 2^32 で巻き戻した位置(32,704)から連続に読んだ値になる(delta −29,796 / +32,704、−68,719 / −68,720 の要素数も一致)。これを受けて、論文の規則 3 を「contiguous な operand のバッチの先頭が要素 2^32 以降にあれば、そのバッチだけが誤答」と書き直した。2^16 要素 / バッチの shape ではバッチの先頭がちょうど要素 2^32 に来るので、書き直す前の形と同じ予測になる。
